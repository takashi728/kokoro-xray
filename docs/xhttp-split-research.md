# XHTTP split upload and download (上下行分离)

Reviewed 2026-11-24 against Kokoro `210d981`. The installer defaults to Xray-core `v26.11.9` in [`lib/geodata.sh`](../lib/geodata.sh); the [upstream release](https://github.com/XTLS/Xray-core/releases/tag/v26.11.9) identifies commit `676eaf6`. [Discussion #4118](https://github.com/XTLS/Xray-core/discussions/4118) shows the original mixed REALITY/CDN topology in both directions. Treat it as a design example, not a versioned config spec. The mode-selection behavior below comes from the pinned source and was cross-checked against [current upstream `main`](https://github.com/XTLS/Xray-core/blob/main/transport/internet/splithttp/dialer.go).

## What splits

- **One VLESS session, two HTTP paths.** The normal outbound supplies the upload address and stream settings. Client-side `xhttpSettings.downloadSettings` supplies an independent `address`, `port`, `network: "xhttp"`, security settings, and nested `xhttpSettings` for the download leg. Xray opens a GET with the same XHTTP session ID used by the streaming upload or numbered upload requests. There is no second VLESS login or secondary outbound. `stream-down` is a runtime label, not a valid JSON `mode`. [Stream configuration](https://github.com/XTLS/Xray-core/blob/v26.11.9/infra/conf/transport_internet.go#L47-L87) · [Dialer](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/dialer.go#L313-L428) · [HTTP requests](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/client.go#L43-L65)
- **`stream-one` cannot split.** It carries both directions in one request; the parser rejects it with `downloadSettings`. The pinned client's `auto` means `packet-up` for TLS (including H2 and H3) and `stream-up` for REALITY when split (`stream-one` without split). Explicit `packet-up` or `stream-up` can split; server `auto` accepts both. Start with TLS `packet-up` for CDN uploads; only try streaming uploads after verifying that the CDN path handles them without buffering or interruption. Do not use the older TLS/H2 `auto` table in #4118 for this pin. [Mode parser](https://github.com/XTLS/Xray-core/blob/v26.11.9/infra/conf/transport_method.go#L300-L317) · [Split guard](https://github.com/XTLS/Xray-core/blob/v26.11.9/infra/conf/transport_method.go#L481-L489) · [Pinned `auto`](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/dialer.go#L312-L325) · [Server mode checks](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/hub.go#L169-L231)
- **Use one JSON layout.** The pin accepts `downloadSettings` directly inside `xhttpSettings`. The older `extra` form also works, but when `extra` exists it replaces the outer XHTTP settings except for `host`, `path`, and `mode`. Adding only `extra.downloadSettings` to Kokoro's current export can silently reset outer padding and XMUX settings. Prefer the direct form and render both legs' compatible padding and session metadata settings explicitly. The outer leg generates the session ID; keep per-leg serialization compatible with the backend, not two independently generated IDs. [Parser](https://github.com/XTLS/Xray-core/blob/v26.11.9/infra/conf/transport_method.go#L261-L317) · [Client metadata](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/client.go#L55-L65) · [Kokoro exporter](../lib/link.sh#L197)

## Server invariant

**Both legs must reach the same XHTTP handler instance.** Each XHTTP listener creates its own in-memory session map. The upload puts bytes in that map's queue; the GET reads that same queue. Neither a shared UUID/path nor two inbounds in the same Xray process makes a shared queue. The GET can return HTTP 200 and flush headers before the VLESS handshake completes, so HTTP success alone is not an end-to-end test. [Listener allocation](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/hub.go#L415-L433) · [Session map](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/hub.go#L34-L88) · [Upload/GET pairing](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/hub.go#L169-L205) · [GET response](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/hub.go#L328-L369)

Kokoro `both` currently sends REALITY to `127.0.0.1:8443` and TLS XHTTP via Caddy h2c to `127.0.0.1:8444`. They are separate handlers. For **TLS/CDN splits**, reuse the existing Caddy TLS site and loopback XHTTP inbound: even different edge addresses, H2/H3, or a direct TLS leg can converge on that same handler. For **mixed REALITY/CDN**, #4118 uses an outer RAW REALITY listener with a VLESS fallback for the decrypted HTTP/2 byte stream; the CDN's HTTP reverse proxy and that fallback both target one cleartext XHTTP listener. This VLESS fallback is distinct from the REALITY TLS `target` and does not put Vision flow on the inner XHTTP session. Kokoro can retain Caddy in place of Nginx, but must prove this topology with the pinned core. The RAW wrapper must let the HTTP preface reach fallback processing (upstream runs VLESS decryption *before* fallback); any optional VLESS payload encryption belongs on the inner shared inbound. Keep the shared listener private and preserve forwarded-header trust boundaries. ## Dial, TLS, and address family

| Input | What it controls |
| --- | --- |
| Upload VLESS `vnext[0].address` / `port`; download `downloadSettings.address` / `port` | Actual remote socket for each leg. Use an explicit IPv4 or IPv6 literal for controlled tests, or a DNS name with a verified single-family result. Validate public reachability from the subscriber network; a VPS interface address alone does not prove it. |
| `tlsSettings.serverName` or `realitySettings.serverName` | TLS identity/SNI, or the configured REALITY server name. For a pinned CDN edge IP, keep TLS SNI set to your proxied hostname and keep certificate verification enabled. A standard Cloudflare HTTP proxy leg uses TLS, not a REALITY handshake to the CDN. |
| `xhttpSettings.host` and `path` | HTTP authority and handler path. The pinned client falls back from explicit `host` to the leg's `serverName`, then to the dial address. Set CDN Host and SNI to the same proxied hostname unless a verified routing configuration needs otherwise. Keep the path and session/padding settings consistent with the shared backend. |

[Pinned XHTTP URL and dial settings](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/dialer.go#L276-L374) · [Pinned TLS and socket dialing](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/dialer.go#L94-L136) · [Cloudflare proxy status](https://developers.cloudflare.com/dns/proxy-status/)

Do not infer family from SNI, Host, or a dual-stack name. With names, resolver and `sockopt` matter; outer `sockopt.penetrate` can override download socket settings in this pin. Cloudflare's public AAAA can be the **edge's** IPv6 address even when the origin uses IPv4; Cloudflare documents preferring IPv4 to a proxied origin with both families. Record client-to-edge and edge-to-origin separately. [Xray DNS dial strategy](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/dialer.go#L208-L248) · [Download socket override](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/dialer.go#L331-L347) · [Cloudflare IPv6 compatibility](https://developers.cloudflare.com/network/ipv6-compatibility/)

## H3 through Cloudflare

Use TLS `alpn: ["h3"]` for a leg deliberately testing QUIC. At this pin only the singleton `h3` selects XHTTP H3; `["h3", "h2"]` is not fallback negotiation for this dialer, and REALITY is always H2. Keep an independent H2 profile for UDP-impaired networks. Cloudflare's HTTP/3 toggle covers **client to edge**, not edge to origin. Keep origin TLS in Full (strict) with a valid matching certificate; Cloudflare can negotiate H2 to Caddy, which can forward h2c locally. No origin UDP 443 is required for CDN H3; leave existing HY2 port ownership alone. Full (strict) validates two TLS legs, not end-to-end TLS through the CDN. [Xray HTTP selector](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/dialer.go#L77-L106) · [Cloudflare HTTP/3](https://developers.cloudflare.com/speed/optimization/protocol/http3/) · [HTTP/2 to Origin](https://developers.cloudflare.com/speed/optimization/protocol/http2-to-origin/) · [Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/) · [Caddy reverse proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)

Xray sets `Cache-Control: no-store` on its streaming response; do not start by adding a zone-wide cache bypass. Check for overrides on the XHTTP path if requests fail. Also check CDN response codes, timeouts, and origin streaming before blaming Caddy or tuning XMUX. A gRPC-shaped streaming upload needs separate compatibility testing; Cloudflare documents its own [gRPC prerequisites](https://developers.cloudflare.com/network/grpc-connections/#requirements) and [origin timeout behavior](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/). [XHTTP response headers](https://github.com/XTLS/Xray-core/blob/v26.11.9/transport/internet/splithttp/hub.go#L328-L347)

## Four mainland route cases

These are test hypotheses, not carrier defaults. Upload and download refer to payload direction from the client. Each leg still needs return traffic: an upload path needs ACKs and responses, and a download path needs a request and ACKs.

| Case | First comparison | Adopt split only when |
| --- | --- | --- |
| 1. Direct IPv4 and IPv6 poor in both directions | Start with both directions through one Cloudflare TLS/H2 hostname, no explicit split. Compare H3 to the same edge and then H2/H3 split if the results differ by direction. | The mixed edge routes or HTTP versions reliably beat the best single-route profile. A poor edge-to-origin path can still cap both legs. |
| 2. Direct IPv4 poor; IPv6 premium in both directions | Test direct IPv6 XHTTP/REALITY H2 in both directions first. Keep CDN TLS/H2 (compare H3 separately) as the alternative for IPv4-only or degraded IPv6 access. | A CDN leg improves a measured directional weakness on reachable IPv6. Don't force weak IPv4 into a winning IPv6 profile. |
| 3. Direct IPv4 upload usable; IPv6 download premium | Keep download direct IPv6 with REALITY H2. Compare direct IPv4 REALITY H2 upload against CDN TLS/H2 `packet-up`, then CDN H3 `packet-up`. | Direct or CDN upload plus the IPv6 download beats the direct-IPv6 and all-CDN baselines. The all-REALITY variant still needs a single dual-stack handler. |
| 4. Direct IPv6 upload premium; IPv4 download usable | Keep upload direct IPv6 with REALITY H2. Compare direct IPv4 REALITY H2 download against CDN TLS/H2 download, then CDN H3 download. | The selected download route improves goodput or stability without losing the IPv6 upload advantage. |

CU169, Telecom 163, CMIN, AS9929, CN2 GIA, and CMIN2 describe candidate routes, not measurements. Select profiles from observed client results; don't infer routes or hardcode a policy from an ASN or commercial label.

## Measurements and implementation gates

1. **Isolate the variables.** From each affected ISP/location, measure direct IPv4 and IPv6 separately in both directions. Against an operator-controlled endpoint, iperf3's normal test sends client-to-server and `-R` sends server-to-client; `-4` / `-6` selects family. Separately measure sustained upload/download through actual Xray profiles to a controlled HTTP endpoint. Raw iperf3 does not exercise the CDN HTTP proxy. Keep payload, concurrency, and timing comparable. [ESnet iperf3 manual](https://software.es.net/iperf/invoking.html)
2. **Test end to end, at more than one time of day.** Compare unsplit H2, unsplit H3, and split with one variable changed at a time. Record connection failures, time to first byte, median and low-percentile goodput, stalls/reconnects, and idle recovery. Confirm both Xray dial destinations, real socket family and ALPN, and origin-side method/status on each leg. Use a large validated upload and download, then deliberately break one leg to ensure the test detects it. A CDN ping, certificate check, or `xray run -test` is not proof of an authenticated round trip.
3. **Keep rendering deterministic.** Represent upload and download as explicit validated inputs to the existing jq renderer; keep DNS discovery, measurements, and apply/reload outside it. Ship an opt-in JSON export and keep unsplit profiles unchanged. First prove TLS/TLS against one backend. Then prove mixed REALITY/TLS in both orientations and IPv4/IPv6 separately. Add no proxy runtime, route auto-selector, origin QUIC listener, or XMUX changes until measurements justify them.

Source review only: no live VPS, client, CDN, or mainland benchmark was run. Split adds a second path and stateful origin dependency; either leg can fail the session. No combination tested or proposed here guarantees GFW reliability.
